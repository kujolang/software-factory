# Disposable SQLite migration qualification

The SQLite subsystem accepts a bounded SQL migration and an independently supplied sealed contract. The contract identifies source and target `user_version`, old schema/data seed statements, expected old rows, expected post-migration SELECT rows, and exact before/after column declarations (name, type, nullability, default and primary-key position). The seal establishes byte identity, not correctness or human approval. Contract review occurs before generation; source/security review and release review use different canonical roles from the backend implementation role.

The controller runs a fixed trusted Node `node:sqlite` harness as UID/GID 65534 in the existing rootless Workcell. It never executes candidate SQL or JavaScript on the host. The normal no-network, read-only root filesystem, private source mount, seccomp, no-new-privileges, resource controls, independent watchdog and cleanup verification remain unchanged. No image rebuild is needed. Exact Node and image identities are declared in `config/sqlite-migration-profile.json`; the narrow SQL profile passed nine actual representative and hostile Workcell cases; see [qualification record](SQLITE-MIGRATION-QUALIFICATION.json).

Each disposable database is seeded with reviewed old data, checked independently, migrated inside a controller-owned transaction, checked for integrity and expected results, closed/reopened, then inspected after a Workcell application restart. A fresh full migration repeats after independent release review. The SQL authorizer rejects attached databases, paths through ATTACH/VACUUM, PRAGMA, explicit transaction/savepoint control, extensions, virtual tables and triggers. Only a bounded allowlist of SQLite scalar/aggregate functions is available. SQL, contract, query rows, output, database pages and execution time are capped. Source/contract files reject links, special files, oversized inputs and unstable reads.

A SQL execution failure rolls back the controller transaction; the evaluator independently verifies the original version, schema and reviewed old rows. A killed process, timeout, failed post-commit assertion or cleanup error is a failed evaluation and does not claim a verified rollback. This does not implement reverse migrations, compatibility with arbitrary production data, online migration, PostgreSQL, framework migrations, automatic deployment or production database access. The finite reviewed fixture is an example of behavior, not exhaustive proof.

`evaluateSQLiteMigration({sqlFile, contractFile, evidenceDir})` is a trusted controller API. `runSQLiteMission({input})` uses native Dispatch and canonical roles, native Spec validation, actual Workcell evaluations, RunLedger terminal accounting and CaseFile failures. Input shape is `kujo.factory.sqlite-mission/v1` with `mission` and `contract`. No model selects the runner, filesystem paths, authorization policy or commands. `verifySQLiteMission` verifies the recorded source/contract/role and Workcell identities before issuing a local reviewed artifact. Production routing remains blocked until its real execution path is qualified.

`node --test tests/sqlite-migration.test.mjs` validates the sealed input and filesystem boundary without an engine or candidate execution. `node scripts/qualify-sqlite-migration.mjs --workcell` performs actual positive migration/restart plus hostile ATTACH, PRAGMA, transaction escape, partial mutation rollback, incorrect data, extension loading output-row overflow and timeout cases. It preserves every failure and records actual source/Workcell receipts. No mocked success qualifies the profile.
