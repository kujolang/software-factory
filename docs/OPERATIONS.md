# Retained mission operations

The operations adapter uses the pinned Dispatch `18b5c737a73904ae942f0bd1c3baa1f77c2bfb40` native `recover inspect` and `recover plan` commands. It does not implement a second scheduler, repair journal history, infer execution completion or automatically resume factory workers.

Before native execution, `bindMissionRecovery(runDirectory)` freezes the immutable mission projection, workflow bytes, frozen pack bytes, exact controller-file inventory, pinned Dispatch revision, repository-source binding and initial application hashes in `artifacts/recovery-binding.json`. The projection includes mission, roles/tasks, provider routing and execution provider, pack identity, team and repository source settings, and required accountability/Lens markers. Status and lifecycle timestamps are excluded so legitimate terminal updates do not invalidate the binding.

`factory operations inspect RUN` reports binding drift, current native step statuses and Dispatch's retained-host assessment. `factory operations plan RUN` also asks native Dispatch for permitted journal/checkpoint repair recommendations. Native source is checked against its pin before invocation. Snapshot paths, file inventories, runtime duration and captured output are bounded; source symlinks and state path mismatches fail closed. Filesystem-preservation handles outside the native run directory require separate owner inspection; this adapter will not probe arbitrary retained host paths. Concurrent checkpoint changes are explicitly reported. Retained `running` state or a leftover lock file does not establish whether a process is alive or dead; liveness is not inferred.

Native structural repair plans explicitly prohibit replay, resume, unconsuming effects and changing policy. Some retained states are unsupported or missing required authority; these remain explicit diagnostics rather than a manufactured successful assessment. `operations inspect` remains a diagnostic; `operations resume-plan` performs separate continuation admission. Only unchanged, quiescent completed-plus-never-started-pending tool boundaries can qualify. Running/failed steps, cached pending effects, approval/control history, inconsistent native journals, changed topology/source/artifacts/controller, terminal accounting and any release approval block continuation. No completed tool or model call is replayed.

## Backups and retention

`factory operations backup RUN DEST` delegates terminal-run export to the existing evidence exporter. It preserves complete selected evidence, source bindings and failures; active runs remain refused. Existing evidence import remains archival, never executable restoration.

`factory operations snapshot RUN DEST` can retain a stable archival copy of active/native recovery state: run/workflow configuration, recovery binding and the complete bounded Dispatch state tree. It checks source identities again before publishing and verifies the staged snapshot. It does not include candidate application bytes, frozen pack contents, provider credentials or full Workcell evidence; use a full terminal backup for those selected mission artifacts. A snapshot does not restore a usable mission or approvals.

`factory operations verify-snapshot PATH` checks exact inventory hashes and rejects missing, changed, extra and symlinked files. This is unsigned integrity verification, not authentication or execution proof. The snapshot and embedded diagnostics can contain private mission information and must remain private unless deliberately shared.

`factory operations retention RUNS` reports a dry-run list for human review, using a 30-day default and explicit terminal timestamps. API callers may choose another positive day count. Missing terminal timestamps retain the run. This legacy report never deletes anything. The separate exact-preview retention interface below provides explicitly authorized archival removal.

## Qualification

`node --test tests/operations.test.mjs` runs the actual pinned native engine with explicitly synthetic offline tools. Tests kill the process group while a native step is running, verify retained uncertainty, inspect/snapshot without reexecution, reject tampering, then independently kill a controller after a durable native approval pause and resume that fixture through upstream `run_workflow`. The completed earlier tool is not repeated; separate fixture result files preserve both observations. No provider, application or external service executes. Tests also verify immutable workflow drift, mutable terminal timestamps and retention dry-run behavior.

This qualifies read-only diagnosis and archival operations on the tested host. Automatic recovery, running-step retry, cross-host runtime restoration, SQLite checkpoint restoration, cost reservation reconciliation, approval replay, source-changing repair and autonomous deletion remain unsupported.

## Authorized same-host continuation

Successful application workers write immutable `artifacts/recovery-checkpoints/TASK.json` after outputs and the completion event. A checkpoint binds the original recovery/configuration/controller identity, all completed task IDs, candidate source and retained artifact inventory. Recovery attempt/checkpoint directories are excluded from recursive inventory; their own records are separately identified. A matching checkpoint is required for any completed work. Legacy runs without checkpoints cannot gain recovery authority retroactively.

The controller calls `prepareMissionResume(RUN, {authorized:true, operator})` to produce a fresh `artifacts/recovery-attempts/attempt-*/authorization.json`. This is local operator attribution, not authentication against a hostile host. The original Dispatch identity, state bytes/revision, checkpoint and source/artifact hashes are bound. The existing adapter loads that original state and uses native `run_workflow_with_admission`; admission is rechecked and consumed once while Dispatch holds its process-owned run lock. It never resets steps, approvals, idempotency or effect claims. Pending tasks run for the first time, preserving existing worker evidence names; completed steps remain skipped by Dispatch. New process/result evidence goes under the attempt directory. A failed admission leaves original state/accounting intact.

`recordMissionCheckpoint` is a controller-worker hook. `admitMissionResume` is the fixed internal admission executable; it is not an unrestricted command/tool interface. Documentation and CLI construction workers may use the same checkpoint hook when their lifecycle has created a recovery binding. Their fixed worker routes and distinct release-authority labels are enforced by the Dispatch adapter.

`node --test tests/operations-resume.test.mjs` kills a real pinned native process at a durable completed/pending boundary, then continues through native locked admission and production checkpoint APIs. Trusted synthetic workers prove the first observation runs once and immutable evidence survives; source mutation, pending cached effects, dependency drift, prior starts and approvals are rejected. These fixtures execute no model or candidate application. A production mission remains subject to its real provider/runtime and independent release gates.

## Global operational admission

`config/operations-policy.json` bounds concurrent controllers, elapsed mission time, inventory size, per-mission/store bytes and minimum free space. All mission kinds share `.runtime/operations/admission` by default, even when their mission stores differ. `acquireMissionAdmission(STORE, RUN, {runId})` atomically reserves a mission lock and capacity slot; the controller retains its record in the immutable mission configuration, passes `lease.check().remainingMs` to the native process timeout, and closes the lease after a reconciled terminal result. Workers call `assertMissionOperationsBudget` before work and at checkpoints. Storage checks operate at admission/task boundaries; they are not filesystem quotas. Existing bounded output, sandbox memory/runtime controls and the independent Workcell watchdog remain necessary.

Abandoned slots are retained. After safe resume assessment, `reclaimMissionAdmissionForResume` can transfer the exact same slot only when the original controller PID is conclusively absent, the owner lineage matches, and explicit local operator authorization exists. A reused/live/inaccessible PID remains unresolved. Old/new owner records are retained in the recovery attempt, and the original deadline is preserved. Partial transfers or changed ownership fail closed. Native execution still requires separate locked admission; a transfer grants no execution or release authority. A failed/nonterminal resume retains the slot for reconciliation rather than assuming the old native owner has stopped.

`node --test tests/operations-policy.test.mjs` verifies capacity across separate stores, duplicate exclusion, storage/deadline limits, retained stale slots, and transfer after killing a real controller process. It does not execute candidate code or an engine.

`operations restore-archive BUNDLE DEST` delegates verified evidence import and explicitly returns `resumeAuthorized:false`. Archival evidence is not the original authoritative native checkpoint. An imported bundle cannot be resumed in place; starting new work requires a separately reviewed mission.

Legacy tool runs have an empty control journal. Upstream retained-host `recover inspect` requires a nonzero control cursor and reports these as unsupported. Factory continuation admits only an empty zero-cursor journal with no retained effect or approval authority; the native runner still performs its own journal reconciliation under the run lock before factory admission. Nonempty retained-host histories require separate reconciliation and are not supported by this continuation path.

## Exact-preview local retention

`retentionCommand` in `factory/operations-retention.mjs` provides `preview RUNS`, `apply PREVIEW.json ARCHIVES SHA256 --operator NAME --authorize-delete`, `verify-archive ARCHIVE`, and `restore-archive ARCHIVE DEST`. CLI routing is separate from this controller API. Save the returned preview JSON outside the mission store and review its exact SHA256 before applying. Only completed missions with an explicit terminal timestamp older than 30 days qualify by default. Failed, cancelled, interrupted, active, recent and undated missions remain retained. Failed attempt evidence inside an otherwise completed mission is copied with all other bytes.

Apply requires both explicit deletion authorization and the exact preview digest. It reserves the same global mission lock used by admission, rejects changed source identities/content/status, and copies the complete bounded mission into a private archive outside the mission store. It verifies every file hash and empty directory before moving the original into a uniquely named quarantine, rechecking it, then removing it. A durable archive intent precedes that move; a result receipt follows removal. A crash can leave a lock, archive or quarantine requiring human reconciliation; none is automatically reclaimed or deleted. A batch can partially complete, with separate receipts for each completed mission.

These archives preserve all mission files, including private raw logs omitted by portable evidence export. Keep them private; this is local storage maintenance, not a safe-to-publish evidence format. Limits are 512 MiB, 20,000 entries and depth 24 per mission; symlinks, hardlinks and special files fail closed. Archiving requires temporary free space and does not reduce total bytes until an operator moves the archive to separate storage. Byte integrity is unsigned and establishes neither authenticity nor execution proof. Retention does not delete archived evidence.

Archive restore verifies and copies into a nested `payload` directory, preserving the distinction between archival recovery and registered executable mission state. It does not acquire approvals, register a mission, restore process liveness, or authorize resume. `node --test tests/operations-retention.test.mjs` verifies complete archive/removal/restore, failed evidence preservation, active admission exclusion, stale previews and terminal status, explicit authorization, tamper rejection and link rejection using temporary fixtures only.

## Operator checkpoint interruption window

`FACTORY_PAUSE_BEFORE=architecture factory run ...` deliberately opens a bounded interruption window before the named task is persisted or executed. The task must be declared, serial and part of an admitted mission. The fixed trusted helper writes `checkpoint-pause.json` and waits no longer than 60 seconds or the original remaining mission deadline. Send SIGTERM to the controller during this window; its existing shutdown handler kills and reaps the native command group. The window does not approve anything and does not itself prove safe recovery. If it expires, execution fails closed instead of starting the selected task. Remove the environment variable before an explicitly authorized `factory resume`; inheriting it during resume is rejected.

This is an operator-requested interruption using Dispatch's synchronous lifecycle hook, not a new scheduler or a protected approval pause. Native approval/control pauses retain their separate authority and remain ineligible for this narrow recovery path. Source/configuration/checkpoint validation and native locked admission still govern whether interruption can resume.

`scripts/qualify-production-recovery.mjs --live` is an opt-in production qualification harness requiring a real provider and qualified Workcell. It starts the converter mission through the public CLI, interrupts after the real command worker, then invokes public authorized resume and requires actual independent release. It preserves logs, assessments and failures. Merely installing this harness or passing its helper tests does not qualify the live path; consult its actual retained result. Controller sources must remain unchanged throughout a live run.

The real Codex command worker completed once; controller SIGTERM returned 143, safe assessment admitted the original completed/pending native state, and authorized resume reached actual v3 release. Command receipt and checkpoint bytes were unchanged, original deadline was retained, and attempt-specific admission/transfer/process/result receipts were present. Actual verification attempt 1 failed and its evidence remained after successful correction. Audit, portable export and offline verification passed (bundle `sha256:78787a739a73141fa51f84c801b244b1ec1bb490804727f8ddf3a865387e9b15`). Observed usage was 122,472 input and 19,406 output tokens; cost was unavailable.
