# Existing repository repair preparation

`factory/repository-mission.mjs` provides the preparation boundary for the standard Node repair path. It accepts a normal local Git repository, an operator mission, a reviewed/sealed software pack and a fresh run application path. It copies committed source into an isolated Git worktree and materializes only `server.mjs`, optional `db.mjs`, and flat `public/*.html`, `*.css`, `*.js`, `*.svg` assets. Original dirty/untracked changes are excluded. Original source, documentation and tests are untouched.

This is a narrow compatibility path for the dependency-free Node 26 ESM/static-browser software-pack runtime. Dependency and development-dependency declarations, package lockfiles, workspaces, package import maps and vendored dependencies are refused. Public asset subdirectories and other formats are unsupported. Static local imports must target admitted implementation files; backend `node:` builtins are allowed. CommonJS and explicit dynamic imports are refused. Import admission uses a conservative lexical scan, not a complete JavaScript parser or security proof; unusual syntax can require manual adaptation. No candidate JavaScript is evaluated on the host. Workcell isolation and independent acceptance remain mandatory.

`prepareRepositoryMission({source, packFile, mission, runDirectory, parent?})` requires that `runDirectory/application` does not already exist. It records the exact original commit, tree, selected file hashes, frozen pack hash and operator mission hash in `artifacts/repository-source.json` and a private binding. Git metadata lives outside the run evidence tree under the private repository-mission directory. The returned binding supplies the source provenance for controller accounting; it does not establish correctness or approval.

After an independently approved, completed, natively accounted local release, `prepareRepositoryPatch(runDirectory)` rechecks the existing release evidence, source and pack bindings, operator mission identity, and unchanged isolated worktree. It copies only approved implementation files into that worktree, removes obsolete admitted implementation assets, and records a reviewable diff. New files receive Git intent-to-add entries so their contents appear in the diff. No commit, push, PR creation, merge or deployment occurs. Generated `package.json`, README, build scripts, changelogs and tests do not overwrite original repository files. Existing project checks still require their own qualified execution; a factory pack does not silently replace them.

An altered worktree, changed pack/operator mission, unapproved run or inconsistent release evidence blocks patch preparation. Interrupted patch writes require inspecting/reconciling the private worktree; the helper does not repeat mutations automatically. Retain private source bindings until patch review is complete. Moving/importing run evidence alone does not recreate the original private Git workspace.

## Qualification

`node --test tests/repository-mission.test.mjs` uses real disposable Git repositories and sealed pack fixtures to check committed source selection, original-file preservation, import/dependency rejection, fresh-run and symlink boundaries, changed-seal refusal and unapproved patch refusal. The fixture code is not executed on the host.

A separate recorded-approval compatibility replay exercised the positive patch path against the retained converter release, producing a nonempty uncommitted diff. That replay uses previously verified code; it is not a newly executed repair mission, provider run or acceptance result. A complete issue-to-repaired-release workflow still requires a live mission through independent Workcell acceptance and review. Arbitrary Node projects, package-managed applications and other language repositories are not supported by this helper.
